== Exercise 4: Models as a Service

The small CPU-hosted model you deployed helped you learn how model serving works. For {company_name}'s more demanding use cases, {assistant_name} uses a larger model: `qwen3-235b-a22b`, hosted on GPU infrastructure by the platform team.

Rather than asking each application team to deploy and manage its own model, the bank provides shared models through Models-as-a-Service (MaaS). The platform team manages the deployments and controls access, while application teams consume the models through an API.

image::fed-aura-platform-architecture-maas-focus.svg[Platform architecture highlighting Models as a Service,link=self,window=blank,width=700]

In this exercise, you'll explore the `qwen3-235b-a22b` endpoint available to you and try it in the playground. In the next exercise, you'll create an API key to use it from code or other tools.

== Exercise 5: Generate an API Key

MaaS uses API keys to control access to shared models, apply rate limits, and track usage. Earlier, the Playground created a temporary key on your behalf so you can test the model quickly. Now, let's create your own API key to call the model from code or other tools.

. Go to *API Keys* page, and click *Create API Key*.

. Give the key a name, for example `my-key`. You can add a description if you wish.

. Select the *Premium Tier* subscription. The subscription defines the model you have access to and the rate limits for the key. Observe that you have 10,000 tokens per minute as the rate limit for `qwen3-235b-a22b`. 
+
image::inference-maas-create-api-key.png[Create API key dialog showing the Premium Tier subscription, the models it covers, and a 30 day expiration,link=self,window=blank,width=700]

. Change the expiration date by selecting *After* from the drop down and make it 30 days. 

. Click *Create API Key*.
+

== Section Summary

You started with a model in a catalog and ended with a production-grade inference platform. Here is what that progression looked like:

* *Model Catalog* - models don't just appear in production. They go through a governed library with metadata about origin, license, and validation status before anyone can deploy them.
* *Single-replica vLLM* - deploying a model is straightforward, but a single replica under concurrent load becomes a bottleneck with no intelligent routing.
* *llm-d* - adding replicas only helps if requests are routed smartly. llm-d tracks replica load and distributes work to minimize wait time across the pool. The API and the user experience stay identical. The improvement is entirely under the hood.
* *Models as a Service* - even well-distributed inference creates chaos if every team manages their own stack. MaaS puts a shared gateway in front: one endpoint, scoped API keys, rate limits, and usage visibility per consumer.

*Key takeaway:*

Each layer solved a real problem the previous one left open. The result is not just a running model, it is a platform that scales, governs access, and gives the platform team observability over who uses what.

NOTE: Want to understand how MaaS is configured under the hood (the Kubernetes custom resources, subscription model, and auth policy chain)? See the optional xref:02-inference/05-maas-configuration.adoc[2.5 MaaS Configuration] page.
