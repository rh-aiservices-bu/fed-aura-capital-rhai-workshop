You built {assistant_name}, tested her, and everything looked good. But the model is just one variable. The documents behind RAG will change as policies update. New tools will be added to the MCP catalog. Someone will tweak the system prompt. Any of those changes — without a model update — can shift her behavior in ways that are hard to spot until something goes wrong in production.

Continuous evaluation is how you stay ahead of that — automated pipelines that measure quality on every change, before it reaches production.

Here is what the results mean:
+
--
* **Evaluation score (96%)** — the overall pass/fail score. The benchmark threshold is set to 0.6 (60%), so anything above that is a *Pass*. This model scored well above the bar.
* **prompt_level_strict_acc (0.94)** — the fraction of prompts where the model followed _every_ instruction exactly. Strict means no partial credit — if a prompt asked for a numbered list in uppercase and the model did one but not the other, it fails that prompt.
* **prompt_level_loose_acc (0.92)** — same as above but with more lenient matching. Minor formatting deviations are tolerated.
* **inst_level_strict_acc (0.96)** — accuracy at the individual _instruction_ level rather than the whole prompt. A prompt may contain multiple instructions (e.g., "write in French" + "use bullet points"); this metric scores each one independently.
* **stderr values** — the standard error across the test set, giving you a sense of how stable the score is.
--
+
NOTE: IFEval measures instruction-following capability, not mortgage-specific quality. It is a useful baseline — if a model can't follow explicit formatting constraints, it will also struggle with tool call schemas and system prompt rules in production. A sudden drop in IFEval scores after a model update is a signal that something changed in the model's core compliance behavior. Domain-specific evaluations are what tell you whether {assistant_name} is answering {company_name}'s questions correctly.


== Exercise 7: Evaluate RAG Quality with RAGAS

RAGAS is a framework that evaluates three things:

* **Faithfulness** — does the answer accurately reflect what was in the retrieved context, or did the model add or change information?
* **Answer relevancy** — does the answer actually address the question asked?
* **Context precision** — did the retrieval step surface the right document chunks, or did it retrieve irrelevant content?

. Go to your Workbench: *OpenShift AI Dashboard > Data Science Projects > wksp-{user} > Workbench*. If you haven't created a workbench yet, follow the steps in xref:02-inference/04-access-a-model-through-maas.adoc#_exercise_7_optional_use_opencode_with_maas_as_your_coding_assistant[Exercise 7] to set one up.

. Let's clone this repository to get the evaluation notebooks. Open up a terminal by clicking the *hamburger menu* (☰) at the top-left corner, then selecting *Terminal > New Terminal*. In the terminal, run:
+

----
+
(or you can ask OpenCode that you set up in the Module 2.4 to clone the repo for you 🤭)
+
. Go to folder `fed-aura-capital-rhai-workshop/notebooks` and open the notebook `04-evaluate_ragas.ipynb`:

. Review the output metrics. Pay attention to:
+
* *Faithfulness* — if this is low, the model is adding information that was not in the retrieved documents
* *Answer relevancy* — if this is low, the model is answering a question it made up rather than the one asked
* *Context precision* — if this is low, the retrieval step is pulling in the wrong document chunks

TIP: If faithfulness is low but context precision is high, the model has the right documents but is ignoring them — it's answering from its own training data instead of what you gave it. If context precision is low, the system is pulling in the wrong documents when it searches, so the answer has nothing good to work with. Both cases point to different things to fix: the first is a model behavior issue, the second is a search quality issue.

== Exercise 8: MLflow llm-as-judge

RAGAS requires a test set with known source documents. But what about open-ended agent evaluations — where you don't have a single correct answer to compare against?

That is where llm-as-judge comes in. Instead of scoring against a ground truth, you use a second LLM to evaluate the quality of the first LLM's responses. The judge model reads the question, the context the agent had available, and the agent's answer, then scores dimensions like correctness, helpfulness, and groundedness.

. Open `evaluate_agent.ipynb` from the `notebooks/` folder:
+
image::evals-agent-notebook.png[Jupyter notebook evaluate_agent.ipynb open in the Workbench,link=self,window=blank,width=700]

. Run the cells in order. The notebook walks through several stages:
+
--
.. *Register a system prompt* — the agent's system prompt is registered in MLflow's Prompt Registry as a versioned artifact. This lets you track quality across prompt iterations and answer "which prompt version caused this regression?"
.. *Create an evaluation dataset* — six mortgage-related test cases are created on the MLflow server, each with an input question, expected keywords, expected tool calls, and forbidden content
.. *Simple evaluation* — three deterministic scorers run first (no LLM calls):
*** `contains_expected` — does the response contain the expected keyword?
*** `has_numeric_result` — does the response include dollar amounts or percentages?
*** `response_length` — is the response at least 50 characters?
.. *LLM-as-a-Judge evaluation* — a second LLM scores each response on:
*** `ToolCallCorrectness` — did the agent call the right tools?
*** `RelevanceToQuery` — is the response relevant to the question?

NOTE: llm-as-judge is not infallible — the judge model has its own biases and limitations. It is most useful for catching obvious regressions (a response that stopped following the persona, a tool call that produced a wrong calculation) rather than for fine-grained quality comparison.

== Exercise 9 (Optional): Run an Evaluation Pipeline

The notebook-based evaluations above are great for exploration. For production, you want evaluation running automatically as a scheduled pipeline — not something a person has to trigger manually. This is the same evaluation you ran in Exercise 8, but packaged as a pipeline that can run without a notebook, on a schedule, in its own container.

WARNING: This exercise requires a few extra minutes. Skip it if you are short on time and continue to the Section Summary.

The pipeline packages the simple evaluation into four automated steps:

* *setup-mlflow-op* — configures the MLflow tracking URI, workspace, and experiment
* *create-dataset-op* — creates the evaluation dataset on the MLflow server (the same 6 test cases from Exercise 8)
* *run-simple-eval-op* — runs the three deterministic scorers (`contains_expected`, `has_numeric_result`, `response_length`)
* *report-results-op* — prints the evaluation summary and logs results

. First, download the pipeline definition file to your local machine: https://raw.githubusercontent.com/rh-aiservices-bu/fed-aura-capital-rhai-workshop/main/collateral/eval-pipeline.yaml[eval-pipeline.yaml,window=blank].

. Navigate to *OpenShift AI Dashboard > Develop & train > Pipelines > Pipeline definitions*. Click *Import pipeline*.
+
image::evals-pipeline-definitions.png[Pipeline definitions page with Import pipeline button highlighted,link=self,window=blank,width=700]

. In the import dialog, select *Upload a file* and upload the `eval-pipeline.yaml` file you downloaded. The pipeline name will auto-populate as `agent-simple-evaluation-pipeline`. Click *Import pipeline*.
+
image::evals-pipeline-import.png[Import pipeline dialog showing eval-pipeline.yaml uploaded,link=self,window=blank,width=700]

A drop in evaluation score blocks the deployment — the same way a failing unit test blocks a code merge.

=== Key Takeaways

* Benchmarks like IFEval measure baseline model capability — they catch model-level regressions (e.g., a model that stops following formatting instructions) but do not measure domain-specific quality
* RAGAS decomposes RAG quality into components (faithfulness, relevancy, precision) so you can diagnose exactly what is going wrong and where
* llm-as-judge enables evaluation of open-ended responses where there is no single correct answer — useful for catching persona regressions and reasoning failures
* Automated evaluation pipelines remove the human from the quality gate — quality is measured continuously and can be scheduled or triggered on every change
