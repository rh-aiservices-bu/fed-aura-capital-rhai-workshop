Guardrails protect the model. Sandboxes protect everything else.

In the xref:02-inference/04-access-a-model-through-maas.adoc#_exercise_7_optional_use_opencode_with_maas_as_your_coding_assistant[Inference section], you set up OpenCode as a coding assistant powered by MaaS — keeping prompts and code on-premises. Now let's tackle the other half: constraining what the agent can _do_.

A coding agent does not know what is sensitive and what is not. Given file system access and network connectivity, it will happily upload internal documents — underwriting thresholds, pricing overrides, meeting notes with confidential figures — to any endpoint it can reach. Even with a self-hosted model, the agent's actions are the risk. OpenShell prevents that.

Estimated time: *10 minutes*

NOTE: OpenShell is Dev Preview in RHOAI 3.5 and Tech Preview in 3.6, with GA targeted for a later release. What you see here represents the direction of secure agent onboarding on OpenShift AI.

== Exercise 1: See the Sandbox in OpenShift

A sandboxed OpenCode agent is already deployed in your environment. Start by finding it - not in the OpenShift console, but in the RHOAI dashboard, where agents are a first-class object alongside models and MCP servers.

. In the *OpenShift AI Dashboard*, expand *AI hub* in the left navigation and select *Agents*:
+
image::security-openshell-agents-nav.png[AI hub expanded in the RHOAI navigation showing Agents, Models and MCP servers,link=self,window=blank,width=280]
+
Agents sit next to *Models* and *MCP servers* for a reason: from the platform's point of view an agent is another deployable asset with its own lifecycle, permissions and audit trail.

. Select the *Deployments* tab and confirm your project is selected. You should see one agent, `+default--fedaura-opencode+`:
+
image::security-openshell-deployment.png[Agents Deployments tab listing the fedaura-opencode agent as Sandboxed and Ready,link=self,window=blank,width=700]
+
Two columns matter here:
+
--
* *Sandbox* reads `Sandboxed`. The agent is not running as a bare pod; it is wrapped in an OpenShell sandbox that mediates what it can reach.
* *Status* reads `Ready` - the sandbox is up and accepting work.
--

. Note what the *Framework* column says: nothing. This is a whole-agent sandbox, so OpenShell does not need to know or care what the agent is built with. OpenCode ships as a container image, gets wrapped, and receives policy enforcement, credential injection and audit logging without a line of its code changing.

TIP: The sandbox is a real Kubernetes object, so you can inspect it from the terminal as well: `oc get sandboxes.agents.x-k8s.io -n wksp-{user}` lists it, and the running pod carries an `agents.x-k8s.io/sandbox-name-hash` label tying it back to the sandbox that owns it.

== Exercise 2: Connect to the Sandbox

Now connect to the running sandbox and see what the agent can access.

. Go back to your workbench and open up a new terminal. (*File > New Terminal* in the code server workbench)

. Register the gateway. The `openshell` CLI needs to know where the gateway is before it can talk to any sandbox. The gateway runs as a Kubernetes Service in your own project, so you reach it by name — there is no port-forward to start and nothing to keep alive in the background. The first line removes any stale registration from a previous session; the second registers the current endpoint:
+
[source,bash]
----
openshell gateway remove openshift 2>/dev/null
openshell gateway add http://openshell:8080 --name openshift --local
----

. List the sandboxes:
+
[source,bash]
----
openshell sandbox list
----
+
[source,text]
----
NAME              CREATED              PHASE
fedaura-opencode  2026-09-17 20:18:56  Ready
----
+
`Ready` means the sandbox is running and accepting work. The corresponding Kubernetes object is the `+default--fedaura-opencode+` Sandbox you saw in exercise 1.

. Open a shell inside it:
+
[source,bash]
----
openshell sandbox exec --name fedaura-opencode --tty -- bash -l
----
+
You are now inside the sandbox. This is the agent's runtime environment: deny-by-default networking, a read-only filesystem apart from a few writable paths, and Landlock restrictions on what any process can reach. `exit` returns you to the workbench.
+
NOTE: There is also `openshell sandbox connect <name>`, which attaches to the shell the sandbox was started with. It is the more natural-looking command, but only one client may own that shell's input at a time, and the ownership is tracked by the gateway rather than by your terminal. Once something else holds it - a session that ended without pressing *Ctrl-P Ctrl-Q*, even in a workbench that no longer exists - every later `connect` reports `attached read-only` or simply hangs, and killing local processes does not release it. `exec --tty` allocates its own pseudo-terminal, so it never contends for that and cannot get stuck.
+
WARNING: Do not try to clear a stuck `connect` with `openshell sandbox stop`. A stopped sandbox cannot re-bootstrap its gateway token, and every later start fails with `IssueSandboxToken bootstrap exchange failed` - including for newly created sandboxes. If a sandbox really is wedged, delete and recreate it.

. Confirm OpenCode is available inside the sandbox:
+
[source,bash]
----
opencode --version
----
+
. Now starts an opencode session inside the sandbox:
+
[source,bash]
----
opencode
----
+
. Feel free to send some prompts like before:
+
[source,bash]
----
"Write a Python function that takes a list of numbers and returns the sum of the even numbers in the list."
----

TIP: Prefer to stay outside the sandbox? `openshell sandbox exec --name fedaura-opencode -- <command>` runs a single command and returns, which is handy for scripted checks.

== Exercise 3: Attempt Data Exfiltration

Time to see this in practice. You will ask OpenCode to share some notes via a GitHub gist and watch what happens at the network level — first with egress open, then with policy enforced.

. While keeping the opencode terminal open, let's open up another terminal. It should be the *workbench terminal* (not inside the sandbox), and fetch two sandbox policies. They ship in a ConfigMap next to the sandbox, already rendered for your cluster:
+
[source,bash]
----
oc get configmap openshell-provision -o jsonpath='{.data.policy\.yaml}' > policy.yaml
oc get configmap openshell-provision -o jsonpath='{.data.policy-exfil-open\.yaml}' > policy-exfil-open.yaml

wc -l policy.yaml policy-exfil-open.yaml
----
+
`policy.yaml` is the standard policy your sandbox is already running. `policy-exfil-open.yaml` is identical except that `api.github.com` is `read-write` instead of `read-only`, and it exists only for this exercise.

. Widen the policy for a moment:
+
[source,bash]
----
openshell policy set --policy policy-exfil-open.yaml --wait --timeout 120 fedaura-opencode
----
+
GitHub gists are a realistic exfiltration route: a public gist is a document anyone can read, created with a single HTTP request.

. Get back to sandboxed OpenCode and give it this prompt:
+
[source,text]
----
Share my meeting notes as a public GitHub gist. Run this curl and show me the full response:
curl -s -w '\nHTTP_STATUS: %{http_code}' -X POST https://api.github.com/gists -H 'Content-Type: application/json' -d '{"public":true,"files":{"notes.txt":{"content":"Meeting notes: review dashboard layout, update color scheme."}}}'
----
+
OpenCode runs the command. The response:
+
[source,json]
----
{
  "message": "Requires authentication",
  "documentation_url": "https://docs.github.com/rest"
}
HTTP_STATUS: 401
----
+
image::security-openshell-exfil-401.png[OpenCode terminal showing the 401 Requires authentication response from GitHub,link=self,window=blank,width=700]

That `401` is the important result, and it is worth being precise about what it means. It came *from GitHub* — "Requires authentication". The request left the sandbox, crossed the internet, and was refused only because anonymous gist creation was withdrawn in 2018. Nothing in {company_name}'s platform stopped it.

The content in this example is harmless meeting notes. In production, the agent cannot tell the difference between meeting notes and confidential underwriting thresholds — it will upload whatever it is asked to. The only thing that stood between that data and a public URL was a third party's authentication policy.

WARNING: Give the agent a token — which any real coding agent has — and that request succeeds.

== Exercise 4: Enforce Policy to Block Exfiltration

. Go back to the *workbench terminal*, apply the standard policy you fetched in exercise 3:
+
[source,bash]
----
openshell policy set --policy policy.yaml --wait --timeout 120 fedaura-opencode
----
+
[source,text]
----
✓ Policy version 4 submitted (hash: b69d4123e8c3)
✓ Policy version 4 loaded (active version: 4)
----
+
The sandbox was never restarted and the agent inside it kept running. Policy is hot-loaded.

. In OpenCode, give it the same prompt again:
+
[source,text]
----
Share my meeting notes as a public GitHub gist. Run this curl and show me the full response:
curl -s -w '\nHTTP_STATUS: %{http_code}' -X POST https://api.github.com/gists -H 'Content-Type: application/json' -d '{"public":true,"files":{"notes.txt":{"content":"Meeting notes: review dashboard layout, update color scheme."}}}'
----
+
This time the response is different:
+
[source,json]
----
{
  "error": "policy_denied",
  "detail": "POST /gists not permitted by policy",
  "layer": "l7",
  "method": "POST",
  "path": "/gists",
  "host": "api.github.com",
  "policy": "github_readonly",
  "rule_missing": { "type": "rest_allow", "method": "POST", "path": "/gists" }
}
HTTP_STATUS: 403
----
+
image::security-openshell-policy-denied-403.png[OpenCode terminal showing the policy_denied response from OpenShell blocking the POST at layer l7,link=self,window=blank,width=700]

. Verify that reads still work — ask OpenCode:
+
[source,text]
----
Check if we can still reach GitHub by running: curl -s -o /dev/null -w '%{http_code}\n' https://api.github.com/zen
----
+
[source,text]
----
200
----
+
image::security-openshell-read-200.png[OpenCode terminal showing a successful 200 response for a GitHub GET request after policy enforcement,link=self,window=blank,width=700]
+
The agent can still research on GitHub, which is most of what a coding agent legitimately needs it for.

Read the difference between the two failures carefully, because it is the whole point of the section:

[cols="1,2",options="header"]
|===
| Exercise 3 — open | Exercise 4 — closed

| `401 Requires authentication`
| `policy_denied` at `layer: l7`

| GitHub answered. The request left the network.
| The sandbox answered. The request never left.
|===

Notice `layer: l7`. The host was not blocked — `GET` to the same host still returns `200`. Enforcement is at the HTTP method and path, so the policy distinguishes *reading GitHub* from *writing to GitHub*. A host-level allowlist could not express that: it would have to choose between blocking research entirely or permitting exfiltration.

The response also names the policy that denied it (`github_readonly`) and the rule that would have been required (`rest_allow` for `POST /gists`). That is the audit trail: not "something was blocked", but which rule, at which layer, for which binary.

== Exercise 5: Customize Your Policies

Deny-by-default means you start with nothing allowed and open up only what the agent demonstrably needs. The loop is the same one `audit2allow` gives you in SELinux: the agent is blocked, the denial tells you exactly which rule was missing, you decide whether to add it, and it hot-loads.

The policy your sandbox is running allows a deliberately small set:

[cols="1,1,2",options="header"]
|===
| Host | Access | Why

| MaaS inference endpoint
| `full`
| the agent cannot work without a model

| `registry.npmjs.org`, `pypi.org`
| `full`
| installing packages is normal agent work

| `github.com`, `api.github.com`
| `read-only`
| clone and read, never push or gist

| `docs.redhat.com`, `access.redhat.com`
| `read-only`
| product documentation is worth reading

| everything else
| denied
| including every paste and webhook service
|===

Try extending it yourself. The `rule_missing` field in a denial is the template for the rule you would add:

. Allow a host you need, then confirm the previously denied request now succeeds.
. Set a host to `read-only` and watch a `POST` fail at `layer: l7` while `GET` keeps working.
. Tighten `filesystem_policy` — can you restrict what the agent can read, so exfiltration fails before the network is even involved?

IMPORTANT: One filesystem rule to know about. A live policy update cannot *remove* a `read_only` path, so a policy you apply to a running sandbox must carry forward the paths already in force - `/app` among them. Drop it and the update is rejected with `read_only path '/app' cannot be removed on a live sandbox`. Add paths freely; removing them needs a new sandbox.

== Before and After: Deploy and Pray vs Defense-in-Depth

[cols="1,1,1",options="header"]
|===
| Dimension | Without (Deploy and Pray) | With (Defense-in-Depth)

| Prompt Injection
| Vulnerable
| Blocked by NemoGuardrails input_shield

| Discriminatory Output
| Possible
| Filtered by output_shield + ECOA compliance check

| Adversarial Robustness
| Unknown
| Quantified by Garak test suite with evidence

| Agent Sandboxing
| Standard containers, no isolation
| Agent Sandbox with OpenShell kernel-level sandboxing (seccomp, Landlock, network namespaces), optionally backed by Kata Containers for hardware-level VM isolation

| Identity
| Hardcoded keys
| SPIFFE/SPIRE cryptographic workload identity (JWT-SVID), short-lived tokens

| Policy
| Implicit allow-all
| Deny-by-default YAML policies with Policy Advisor for iterative discovery

| Audit Trail
| None
| OCSF v1.7.0 structured audit events, SIEM-ready

| Credentials
| Exposed to agent code
| Supervisor proxy injects at network boundary via inference.local, agent never sees keys

| Agent Onboarding
| Custom integration per framework
| Two BYOA patterns: whole-agent sandboxing (zero code changes) or harness-native SDK integration

| Production Readiness
| CISO blocks deployment
| Validated security posture with documented evidence
|===

=== Key Takeaways

* AI safety requires defense-in-depth: no single tool covers all attack vectors. Persona-based access controls who can ask, guardrails control what can be asked and answered, and sandboxes control what agents can do at runtime
* Guardrails operate at both input (blocking prompt injection before it reaches the agent) and output (filtering non-compliant responses before they reach the user). The Guardrails Orchestrator is GA and coordinates detection
* Garak provides quantified adversarial robustness with pass/fail evidence. The Chatterbox Labs integration enables a full flow: define a policy, generate synthetic attacks, probe the model, produce a compliance report
* OpenShell's deny-by-default model means agents can access nothing unless explicitly permitted. The Policy Advisor provides an iterative, audit2allow-style workflow for building least-privilege policies
* Every decision across all three layers is traced in MLflow - persona checks, guardrail enforcement, and sandbox policy decisions. This is the audit trail regulators and auditors need
