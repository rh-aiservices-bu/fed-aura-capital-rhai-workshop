== Exercise 1: System Prompts - Shaping Model Behavior

A system prompt is a set of instructions given to the model before the user's message. It defines who the model is, how it should behave, and what it knows. In Module 3 you used system prompts to shape persona and tone. Here you will use them to try something different - injecting domain knowledge directly into the prompt.

=== Why this approach breaks down

The system prompt worked. So why not stop here?

IMPORTANT: Prompt engineering is valuable for defining persona and behavior, but it is not the right tool for injecting large, changing knowledge bases. Here is why:

* **Token limits**: A system prompt consumes the model's context window. Five product descriptions fit. An entire underwriting manual, compliance guide, and rate sheet library does not.
* **Maintenance burden**: When rates change or new products launch, someone must update every system prompt manually. There is no single source of truth.
* **Staleness**: The prompt is static text baked into the configuration. It does not know when information becomes outdated.
* **Scale**: {company_name} has policy documents, compliance manuals, rate sheets, product guides, and regulatory filings. You cannot paste all of them into a prompt.

The system prompt should define _who the assistant is_ and _how it behaves_. The knowledge it needs to answer questions should come from somewhere else. That somewhere else is RAG.

[%collapsible]
.How RAG works under the hood (click to expand)
====
When you enabled RAG and uploaded a document, the platform performed several steps automatically:

. **Chunking**: The document was split into smaller passages (chunks) that fit within the model's context window.
. **Embedding**: Each chunk was converted into a vector embedding - a numerical representation that captures its semantic meaning.
. **Storage**: The embeddings were stored in PostgreSQL with the **pgvector** extension, which enables similarity search on vectors.
. **Retrieval**: When you sent your question, the platform embedded your question too, searched pgvector for the most semantically similar chunks, and retrieved them.
. **Augmentation**: The retrieved chunks were injected into the model's context alongside your question, giving the model access to the relevant facts.
. **Generation**: The model composed its response using both its general language capabilities and the retrieved document content.

{company_name}'s production application uses the same stack. **OGX** provides the unified API layer that coordinates retrieval and generation, and **pgvector** provides the vector storage. The Playground's RAG toggle wraps this into a simple upload-and-query experience.
====

== Data Preprocessing and Document Intelligence

The product catalog you uploaded was plain text - clean, structured, and ready for chunking. That made RAG straightforward. But look at the document again: it is a simple `.txt` file with clear headings and consistent formatting.

In a real enterprise, documents rarely look like that. Mortgage companies deal with:

* PDF rate sheets with tables and footnotes
* Scanned compliance documents that need OCR
* Underwriting manuals with charts, decision trees, and embedded images
* PowerPoint presentations from product launches
* HTML pages from regulatory databases

LLMs are fundamentally text-in, text-out systems. Before a model can reason about a chart in a PDF, that chart needs to be converted to structured text. This is where document preprocessing comes in.

=== Docling: Document intelligence for RAG

Red Hat AI includes **Docling** for document preprocessing. Docling uses vision models and layout analysis to identify text blocks, tables, figures, and headers in complex documents. It preserves document structure so that chunking for RAG retains semantic boundaries - it does not split mid-table or mid-paragraph.

IMPORTANT: Explore document preprocessing with Docling in this interactive demo: https://app.arcade.software/flows/RK066swfARYNhOwhilvK/view[Docling Arcade Demo,window=blank]

== Optional: AutoRAG Pipeline

This works for experimentation, but production RAG systems need to handle hundreds of documents, update automatically when new files arrive, and manage chunking and embedding parameters at scale.

AutoRAG provides the same RAG capability as an automated pipeline. You define a data source, configure chunking and embedding parameters, and the pipeline processes documents continuously. When new documents are added, the pipeline re-indexes automatically.

* Knowledge updates happen in minutes (upload a new document) instead of days or weeks (retrain the model)
