== Exercise 3: Deploy with llm-d

In the previous exercise you deployed Qwen3 0.6B on a single node using vLLM. That works for experimentation, but as soon as multiple users send requests at the same time, a single replica becomes a bottleneck. The obvious fix is to add more replicas — but here's the catch: OpenShift's default load balancing routes requests round-robin across replicas without knowing anything about what each one is doing. One replica might be halfway through generating a long response while another is completely idle, and new requests still get spread evenly. The result is unpredictable latency and wasted capacity.

llm-d solves this by replacing the default routing with a scheduler that understands LLM workloads. It knows which replicas are busy, how long each request is likely to take, and how to route new requests to minimize wait time across the whole pool. You get the same vLLM inference engine underneath — llm-d just makes the traffic distribution smarter.

NOTE: In this exercise you are deploying to CPU again. The llm-d architecture and deployment steps are identical on GPU — the only difference is the hardware profile you select.

=== Deploy the Model

. In the *OpenShift AI Dashboard*, go to *AI Hub > Models* and select the *Other Models* tab. Again, find *Qwen3 0.6B* and click *Deploy*.

. Select your project `wksp-{user}` and click *Next*.

. You will be prompted for the model location. Leave the defaults as-is and click *Next*.

. On the deployment configuration screen, keep the name as-is. Under deployment options, select *LLM inference service with llm-d*.

. For *Topology type* keeps `Single node`, and for *Topology configuration* select `Single node on CPU`.

. Then expand `> Customize resource requests and limits` and set the resource values as below:
+
image::inference-cpu-resource-limits.png[Resource requests and limits configuration for llm-d deployment,link=self,window=blank,width=700]

. For *Routing* configuration select `CPU LLM-d scheduling-policy` routing config. It is a load aware intelligent routing, which means requests will be routed to the least busy replica. This is a default routing policy for llm-d, but you can also create your own routing policies for different use cases, such as session aware, prefix-cache aware, predicted-latency based, etc. 

. For *Replica count* set the number of replicas to *2*. Click *Next*:
+
image::inference-llmd-replica-config.png[Replica count set to 2 in the deployment configuration,link=self,window=blank,width=700]
+
NOTE: Two replicas means llm-d will distribute incoming requests across two vLLM instances in a smart way.

. On the next screen, select *Add as AI asset endpoint*. Don't worry about the MaaS option yet.
+
image::inference-ai-asset-endpoint.png[AI asset endpoint configuration,link=self,window=blank,width=700]

. Again, lets add `custom runtime arguments` and pass `--max-model-len=2048` to limit the maximum length of the model's context window to 2048 tokens. 

. Then add `custom runtime environment variables` as `VLLM_CPU_KVCACHE_SPACE=8` to set the size of the key-value cache to 8GB.
+
image::inference-custom-runtime-args-and-env-vars.png[Custom runtime arguments and environment variables,link=self,window=blank,width=700]

Click **Next** and then *Deploy*.

. Wait for the deployment to show a green status indicator. This takes a minute or two while the model weights are pulled and loaded:
+
image::inference-llmd-deployment-ready.png[llm-d deployment showing green ready status with 2 replicas,link=self,window=blank,width=700]

=== Quick Test: GenAI Playground

Let's confirm the model is responding before we move on.

. Go to *Gen AI Studio > AI asset endpoints*. Click *Try in playground* for the Qwen 0.6 model (ignore `gpt-oss-120b` for now). Set *Max tokens* to `1024` and click *Configure*.
+
image::inference-try-in-playground.png[Try in Playground,link=self,window=blank,width=700]

. Send a prompt of your choice — for example:
+
[source,text]
----
Summarize the risks of using a single-node LLM deployment in production.
----
+
(or try something more interesting🤭). You should get a coherent response from the model. The experience looks identical to what you saw in Exercise 2 — and that is the point. llm-d does not change the API or the user experience; it changes what happens underneath, where requests are scheduled and served.

NOTE: You can continue chatting but because we are running a low concurrent load (basically you sending consecutive messages), you won't observe a latency difference compared to the single-replica deployment. In a real workload with many simultaneous users, the two-replica setup would show meaningfully lower latency and higher throughput.

=== What's Next?

You've now deployed the same model two ways: single-node vLLM and distributed llm-d with two replicas. In both cases you talked to the model directly through the Playground.

In the {company_name} organization, application teams don't deploy their own models and talk to model endpoints directly. They go through the MaaS gateway, which adds authentication, rate limiting, and usage metering on top. That's what Exercise 4 covers.
