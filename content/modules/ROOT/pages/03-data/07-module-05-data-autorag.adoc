== Data Preprocessing and Document Intelligence

The product catalog you uploaded was a well-structured PDF - clean headings, consistent formatting, and ready for chunking. That made RAG straightforward.

But look at what a real {company_name} internal document looks like. Open the https://github.com/rh-aiservices-bu/fed-aura-capital-rhai-workshop/blob/dev/collateral/internal-policies-enhanced.pdf[{company_name} Internal Underwriting Policies,window=blank] PDF and scroll through it:

image::module5-docling-example-page1.png[Internal Underwriting Policies page 1 - DTI limits section with bar chart showing ratios by loan type,link=self,window=blank,width=600]

image::module5-docling-example-page2.png[Internal Underwriting Policies page 2 - Jumbo thresholds infographic and rate lock timeline diagram,link=self,window=blank,width=600]

Charts, infographic cards, timeline diagrams, color-coded escalation flows. If you uploaded this PDF to the Playground as-is, RAG would chunk the raw text - but the visuals would be lost or garbled. The model would miss that the conventional DTI limit is 40%, that jumbo loans need 12 months of reserves, or that a 90-day rate lock requires manager approval.

LLMs are text-in, text-out systems. Before a model can reason about a chart in a PDF, that chart needs to be converted to structured text. This is where document preprocessing comes in.

=== Docling: Document intelligence for RAG

**Docling** uses vision models and layout analysis to understand document structure - it identifies text blocks, tables, figures, and charts, then converts them into structured text that preserves semantic meaning.

With the internal policies PDF, Docling converts the DTI bar chart into "Conventional: 40%, FHA Front-end: 31%, FHA Back-end: 43%", the jumbo infographic into "$766,550 conforming limit, 700 min credit score, 38% max DTI", and the rate lock timeline into "30/45/60-day standard locks, 90-day extended lock requires manager approval." Without Docling, those visuals would be invisible to the model. With Docling, they become retrievable facts.

IMPORTANT: Explore document preprocessing with Docling in this interactive demo: https://app.arcade.software/flows/RK066swfARYNhOwhilvK/view[Docling Arcade Demo,window=blank]

== Optional: AutoRAG Pipeline

WARNING: The AutoRAG pipeline takes at least *12 minutes* to complete. This section is optional and intended for participants who want to explore the automated pipeline approach.

The Playground's RAG toggle is a manual workflow - you upload files one at a time and the system processes them on the spot. This works for experimentation, but production RAG systems need to handle hundreds of documents, update automatically when new files arrive, and manage chunking and embedding parameters at scale.

**AutoRAG** is an automated optimization system in Red Hat OpenShift AI that finds the best RAG configuration for your documents. You provide documents and test data, and AutoRAG tests different combinations of chunking, embedding, retrieval, and generation settings. Each combination produces a **RAG pattern** with evaluation scores. AutoRAG ranks patterns on a leaderboard and generates Jupyter notebooks that you can use to run the best pattern.

=== Create an AutoRAG optimization run

. In the OpenShift AI dashboard, expand **Gen AI studio** in the left sidebar and click **AutoRAG**:
+
image::module5-autorag-sidebar.png[OpenShift AI sidebar showing Gen AI studio expanded with AutoRAG Tech Preview option,link=self,window=blank,width=250]

. Click **Create AutoRAG optimization run**. Enter the following details and click **Next**:
+
* **Name**: `fed-aura-autorag`
* **Description**: `Fed Aura Capital AutoRAG`
* **Open GenAI Stack connection**: select `fed-aura-ogx-connection`
+
image::module5-autorag-create.png[Create AutoRAG form with name and OGX connection filled in,link=self,window=blank,width=700]

. In the **Knowledge setup** section, select `minio` as the **S3 connection**. Click **Select file or folder** and then **Browse bucket**:
+
image::module5-autorag-experiment.png[AutoRAG experiment configuration showing Knowledge setup with S3 connection,link=self,window=blank,width=400]

. Select the `docs` folder from the MinIO bucket. This folder contains the {company_name} documents that AutoRAG will index and use for retrieval:
+
image::module5-autorag-select-docs.png[File browser showing MinIO bucket contents with docs folder selected,link=self,window=blank,width=500]

. Under **Configure details**, set the **Vector I/O provider** to `pgvector (remote Pgvector)`. This is the same PostgreSQL vector database used by the Playground RAG:
+
image::module5-autorag-pgvector.png[Vector I/O provider dropdown set to pgvector,link=self,window=blank,width=600]

. For the **Evaluation dataset**, click **S3** to browse the MinIO bucket:
+
image::module5-autorag-eval-section.png[Evaluation dataset section with S3 browse option,link=self,window=blank,width=500]
+
Select `autorag-test-data.json`. This file contains test questions and expected answers that AutoRAG uses to evaluate each RAG configuration:
+
image::module5-autorag-eval-dataset.png[S3 file browser with autorag-test-data.json selected,link=self,window=blank,width=500]

. Change **Maximum RAG patterns** to `4` (default is 8). This reduces the number of configurations AutoRAG tests, which speeds up the run. Leave all other settings at their defaults (optimization metric: Answer faithfulness).

. Click **Create run**. The pipeline starts in **Preparing** status. After a few minutes, refresh the page and click **Hide details** / **Show details** to see the pipeline DAG. Each of the 4 patterns runs through the full RAG pipeline - chunking, embedding, retrieval, generation, and evaluation:
+
image::module5-autorag-running.png[AutoRAG pipeline DAG showing 4 patterns running in parallel with Running status,link=self,window=blank,width=700]

. Wait for the pipeline to complete (up to 20 minutes). When finished, the status changes to **Succeeded** and the right panel shows the results - total run time, number of patterns evaluated, the winning pattern, and the evaluation metric:
+
image::module5-autorag-complete.png[AutoRAG pipeline completed showing Succeeded status with 3 patterns evaluated and Pattern3 as winning pattern,link=self,window=blank,width=700]

NOTE: AutoRAG tests combinations of chunking sizes (1024, 2048), chunk overlap (128, 256), retrieval methods (vector, hybrid), and number of chunks retrieved (3, 5, 10) against the foundation and embedding models available on your OGX instance.

[%collapsible]
.What AutoRAG tests and how to read the results (click to expand)
====
Each RAG pattern is a unique combination of settings that AutoRAG evaluates. The results appear on a leaderboard ranked by three metrics:

[cols="1,2",options="header"]
|===
| Metric | What it measures

| Answer faithfulness
| Whether the answer uses information from retrieved documents rather than hallucinating. High faithfulness means the model stays grounded.

| Answer correctness
| Whether the answer matches the expected answers from your test data. High correctness means the RAG system produces accurate results.

| Context correctness
| Whether the retrieval step finds relevant documents. High context correctness means the right chunks are being retrieved.
|===

After the run completes, you can click any pattern to see its configuration details, per-question scores, and sample Q&A responses. You can also select **Try this pattern** to test it interactively in a chat panel.

=== Key Takeaways

* System prompts define behavior and persona but are not the right tool for large, changing knowledge bases
* RAG grounds model responses in retrieved documents, providing current, organization-specific answers traceable to source text
* A production AI assistant combines RAG (for facts) with a tuned system prompt (for persona and style)
* Enterprise RAG pipelines require document preprocessing to handle PDFs, images, tables, and other complex formats
* Knowledge updates happen in minutes (upload a new document) instead of days or weeks (retrain the model)
