== Exercise 4: Models as a Service

You've been observing a model `gpt-oss-120b` in the AI Asset Endpoints list, but you didn't deploy this one. Well, hate to break it to you but {assistant_name} hasn't been using the little model you deployed. Because the small model you deployed on CPU is not good enough for {company_name}'s use case both in terms of capability and performance. The model that {assistant_name} is using is `gpt-oss-120b`, which is a much larger model and requires GPU to run.

But of course, {company_name} has other AI use cases as well, and they don't want to deploy a model for every use case. Instead, they want to have a model that can be used for multiple use cases. This is where Models as a Service (MaaS) comes in. With MaaS, an admin can expose models as endpoints that can be consumed by different applications and users.

And as a user, you are granted access to the MaaS endpoints that are relevant to your role. That's why you've been seeing `gpt-oss-120b` in the list. You can see the list of available endpoints in the AI Asset Endpoints list, and you can use them in your applications without having to worry about the underlying model deployment and management.

MaaS provides a consistent and governed way to access models, which means {company_name} can manage the model deployments centrally while still providing access to the models for different teams and applications.

== Exercise 6: Consume the MaaS Endpoint with cURL

With your key in hand, let's call the model directly from the terminal.

. Navigate to the *Terminal* tab. Set your API key and endpoint URL as environment variables. Use the key you saved in the notepad above and the endpoint URL from the endpoint detail page:
+
[source,console,role=execute,subs=attributes+]
----
export MAAS_API_KEY=<paste-your-api-key>
export MAAS_URL=<endpoint-url>
----

. Send a completion request:
+
[source,console,role=execute,subs=attributes+]
----
curl -sk $MAAS_URL/v1/chat/completions \
  -H "Authorization: Bearer $MAAS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-oss-120b",
    "messages": [{"role": "user", "content": "What is Models as a Service?"}],
    "max_tokens": 256
  }' | jq -r '.choices[0].message.content'
----
+
You should see a response from `gpt-oss-120b`. The API is OpenAI-compatible — any application that already talks to OpenAI can point at this endpoint instead, with no code changes beyond swapping the base URL and key.

=== On-premises vs cloud inference

Everything you just did ran entirely within the OpenShift cluster. No data left the environment. This is the key advantage of self-hosted inference for regulated industries like financial services: full data residency, no external API dependencies, and inference costs tied to your own hardware rather than per-token cloud pricing.

MaaS gives you the developer experience of a cloud API — stable endpoints, API keys, usage dashboards — with the data control of on-premises infrastructure.

But self-hosted models are not the only thing MaaS can expose. The same gateway can also front external providers like OpenAI, Anthropic, or Gemini. From a user's perspective, nothing changes: you still browse the AI Asset Endpoints list, generate an API key, and call the endpoint the same way. The gateway handles the routing — whether the request goes to a locally deployed model or to an external API is transparent to the consumer. This means teams can use a mix of self-hosted and cloud models without managing separate credentials, SDKs, or rate-limiting policies for each one.

====
You have been using MaaS as a consumer — generating keys, calling endpoints, observing usage. But someone had to set all of this up. Here is what the platform team configured before you arrived, and how the pieces connect.

=== The MaaS object model

MaaS is built on a set of Kubernetes custom resources. When the platform team exposes a model, they are creating and linking these objects:

image::maas-object-model-governance.png[MaaS Object Model and Governance diagram showing AITenant, MaaSSubscription, MaaSAuthPolicy, and model infrastructure CRDs,link=self,window=blank,width=700]

* **AITenant** — bootstraps an isolated MaaS tenant with its own namespace, auth policies, and RBAC. Each team or project gets one.
* **MaaSSubscription** — the central resource that maps users and groups to models, and defines quota and rate limits. Every API key you generate is backed by a subscription.
* **MaaSAuthPolicy** — authorizes specific users or groups to access model endpoints through the AI Gateway. It enforces the access rules at the HTTP level on every request.
* **MaaSModelRef** — points to the actual inference server (an llm-d deployment, a vLLM runtime, or an external provider). The subscription references this to know where to route requests.
* **ExternalProvider / ExternalModel** — when the backend is a cloud provider (OpenAI, Anthropic, Gemini), these resources configure the endpoint, credentials, and model name mapping. From the consumer's perspective, calling an ExternalModel is identical to calling a self-hosted one.

NOTE: Both `MaaSSubscription` (quota) AND `MaaSAuthPolicy` (access) must exist for a consumer to reach an endpoint. Creating a subscription without an auth policy gives you rate limits but no access. The UI's *"Create matching authorization policy"* checkbox creates both at once.

=== Anatomy of a subscription

image::maas-subscription-anatomy.png[Anatomy of a MaaSSubscription showing CR properties, priority scheme, and two-layer governance model,link=self,window=blank,width=700]

A `MaaSSubscription` has three key sections:

* **spec.groups / spec.users / spec.serviceAccounts** — who this subscription applies to. Users inherit quota limits from every subscription they belong to; the highest-priority one wins when limits overlap.
* **spec.priority** — a numeric value that determines which subscription takes precedence. The platform team at {company_name} follows this scheme:
** *100* — production customer-facing apps, strict quotas, billed to the prod cost center
** *50* — staging and pre-release validation
** *0* — development and data science exploration (the default)
** *-10* — personal sandbox and tutorial access (lowest precedence)
* **spec.models and tokenLimits** — which models the subscription covers and the rate limits per model: tokens per request and tokens per time window (RPM/TPM).

TIP: Use priority gaps (10, 20, 30...) between your tiers so you can insert new levels later without renumbering everything.

=== How users, groups, and policies bind together

image::maas-subscription-auth-relationships.png[Subscription, Group and Auth Policy Relationships diagram showing how users bind to subscriptions and how policies are enforced at the gateway,link=self,window=blank,width=700]

When you made an API call in this exercise, the gateway evaluated your request like this:

. Your OIDC token arrived with your user identity and group membership.
. The gateway looked up which `MaaSSubscriptions` include your user or groups.
. It evaluated the subscription priority to determine your effective quota.
. It checked `MaaSAuthPolicy` to confirm you are authorized for the `/v1/chat/completions` endpoint on `gpt-oss-120b`.
. Your request was routed to the model. Usage was recorded against your key.

This all happened in milliseconds, invisibly. The reason it works reliably at scale is that the platform team defined it once as Kubernetes resources — version-controlled, auditable, and repeatable.
