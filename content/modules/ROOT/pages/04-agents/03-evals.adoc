== Exercise 7: Evaluate RAG Quality with RAGAS

General capability benchmarks tell you whether the model is working. RAGAS tells you whether your RAG pipeline is working.

RAGAS is a framework that evaluates three things:

* **Faithfulness** — does the answer accurately reflect what was in the retrieved context, or did the model add or change information?
* **Answer relevancy** — does the answer actually address the question asked?
* **Context precision** — did the retrieval step surface the right document chunks, or did it retrieve irrelevant content?

. Go to your Workbench: *OpenShift AI Dashboard > Data Science Projects > {user_project} > Workbench*.

. Open the notebook `evaluate_ragas.ipynb`. It is already available in your workbench and pre-configured to connect to the RAG pipeline you set up in section 3.2:
+
// TODO: screenshot of evaluate_ragas.ipynb open in Workbench (evals-ragas-notebook.png)
image::evals-ragas-notebook.png[Jupyter notebook evaluate_ragas.ipynb open in the Workbench,link=self,window=blank,width=700]

. Run all cells. The notebook:
.. Sends a test set of mortgage questions through the RAG pipeline
.. Collects the retrieved context and the model's answers
.. Passes everything to RAGAS for scoring

. Review the output metrics. Pay attention to:
+
* *Faithfulness* — if this is low, the model is adding information that was not in the retrieved documents
* *Answer relevancy* — if this is low, the model is answering a question it made up rather than the one asked
* *Context precision* — if this is low, the retrieval step is pulling in the wrong document chunks

TIP: Low faithfulness with high context precision usually means the model is ignoring the retrieved context and answering from training data. Low context precision means the chunking or embedding configuration needs tuning.

== Exercise 8: MLflow llm-as-judge

RAGAS requires a test set with known source documents. But what about open-ended agent evaluations — where you don't have a single correct answer to compare against?

That is where llm-as-judge comes in. Instead of scoring against a ground truth, you use a second LLM to evaluate the quality of the first LLM's responses. The judge model reads the question, the context the agent had available, and the agent's answer, then scores dimensions like correctness, helpfulness, and groundedness.

. In your Workbench, open `evaluate_agent.ipynb`:
+
// TODO: screenshot of evaluate_agent.ipynb open in Workbench (evals-agent-notebook.png)
image::evals-agent-notebook.png[Jupyter notebook evaluate_agent.ipynb open in the Workbench,link=self,window=blank,width=700]

. The notebook runs a set of loan assessment queries through {assistant_name}'s agent and collects the responses. Run the first section of cells to generate the responses.

. The second section configures the judge model and scoring criteria — correctness, groundedness, refusal appropriateness. Run these cells to start the evaluation.

. Results are logged to MLflow automatically. Once the notebook finishes, navigate to *OpenShift AI Dashboard > Develop & Train > Experiments* and find the new evaluation run. Review the per-question scores:
+
// TODO: screenshot of llm-as-judge results in MLflow (evals-llm-judge-results.png)
image::evals-llm-judge-results.png[MLflow experiment showing llm-as-judge evaluation scores per question,link=self,window=blank,width=700]

NOTE: llm-as-judge is not infallible — the judge model has its own biases and limitations. It is most useful for catching obvious regressions (a response that stopped following the persona, a tool call that produced a wrong calculation) rather than for fine-grained quality comparison.

=== Key Takeaways

* Benchmarks like ArcEasy measure baseline model capability — they catch model-level regressions but do not measure domain-specific quality
* RAGAS decomposes RAG quality into components (faithfulness, relevancy, precision) so you can diagnose exactly what is going wrong and where
* llm-as-judge enables evaluation of open-ended responses where there is no single correct answer — useful for catching persona regressions and reasoning failures
* Automated evaluation pipelines remove the human from the quality gate — quality is measured continuously, not just when someone remembers to check
