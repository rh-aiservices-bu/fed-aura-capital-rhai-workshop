== Exercise 3: Deploy with llm-d

In the previous exercise you deployed Qwen3 0.6B on a single node using vLLM. That works for experimentation, but as soon as multiple users send requests at the same time, a single replica becomes a bottleneck. The obvious fix is to add more replicas — but here's the catch: OpenShift's default load balancing routes requests round-robin across replicas without knowing anything about what each one is doing. One replica might be halfway through generating a long response while another is completely idle, and new requests still get spread evenly. The result is unpredictable latency and wasted capacity.

llm-d solves this by replacing the default routing with a scheduler that understands LLM workloads. It knows which replicas are busy, how long each request is likely to take, and how to route new requests to minimize wait time across the whole pool. You get the same vLLM inference engine underneath — llm-d makes the traffic distribution smarter.

NOTE: In this exercise you are deploying to CPU again. The llm-d architecture and deployment steps are identical on GPU — the only difference is the hardware profile you select.

=== Deploy the Model

. In the *OpenShift AI Dashboard*, go to *AI Hub > Models > Catalog* and select the *Other Models* tab. Again, find *Qwen3 0.6B* and click *Deploy*.

. Select your project `Workspace {user}` and click *Next*.

. You will be prompted for the model location. Leave the defaults as-is and click *Next*.

. On the deployment configuration screen, keep the name as-is. Under deployment options, select *LLM inference service with llm-d*.

. For *Topology type* keeps `Single node`, and for *Topology configuration*, from the drop down menu, select `Single node on CPU`.

. Then expand `> Customize resource requests and limits` and set the resource values as below:
+
image::inference-cpu-resource-limits.png[Resource requests and limits configuration for llm-d deployment,link=self,window=blank,width=700]

. For *Routing* configuration, from the drop down menu, select `CPU LLM-d scheduling-policy` routing config. It is a load aware intelligent routing, which means requests will be routed to the least busy replica. This is a default routing policy for llm-d, but you can also create your own routing policies for different use cases, such as session aware, prefix-cache aware, predicted-latency based, etc. 

. For *Replica count* set the number of replicas to *2*. Click *Next*:
+
image::inference-llmd-replica-config.png[Replica count set to 2 in the deployment configuration,link=self,window=blank,width=700]
+
NOTE: Two replicas means llm-d will distribute incoming requests across two vLLM instances in a smart way.

. On the next screen, select *Add as AI asset endpoint*. Don't worry about the MaaS option yet.
+
image::inference-ai-asset-endpoint.png[AI asset endpoint configuration,link=self,window=blank,width=700]

. Make sure you *unchecked* the *Token authentication* option.

. Again, lets add `custom runtime arguments` and pass `--max-model-len=2048` to limit the maximum length of the model's context window to 2048 tokens. 

. Then add `custom runtime environment variables` as `VLLM_CPU_KVCACHE_SPACE=8` to set the size of the key-value cache to 8GB.
+
image::inference-custom-runtime-args-and-env-vars.png[Custom runtime arguments and environment variables,link=self,window=blank,width=700]
+
Click **Next** and then *Deploy*.
+
. While waiting for the model to deploy, go to the *Terminal* tab and run the following command to list the pods created by the llm-d deployment:
+
[source,bash]
----
oc get pods -n wksp-{user} -l app.kubernetes.io/part-of=llminferenceservice
----
+
You should see *2 replicas* of the same model, alongside a *router pod*. The router is responsible for deciding which replica is most suitable to handle each incoming request, based on factors like current load and cache state.
+
image::inference-llmd-pods-terminal.png[Terminal showing llm-d pods with 2 replicas and a router,link=self,window=blank,width=700]
+
. Let's go back to RHOAI Console and wait for the deployment to show a green status indicator. This takes a minute or two while the model weights are pulled and loaded:
+
image::inference-llmd-deployment-ready.png[llm-d deployment showing green ready status with 2 replicas,link=self,window=blank,width=700]

In a real workload with many simultaneous users, the two-replica setup would show meaningfully lower latency and higher throughput.

=== What's Next?

You've now deployed the same model two ways: single-node vLLM and distributed llm-d with two replicas. In both cases you owned the deployment end-to-end — you decided the model, the resources, the replicas.

Now imagine every team at {company_name} doing the same thing. The borrower team deploys their own model. The underwriting team deploys theirs. The CEO dashboard team deploys another. Each one holds GPU capacity for its own use, sits mostly idle between requests, and bills to no one in particular. There's no visibility into who deployed what, how much each team is consuming, or whether a model is even being used. When something breaks, nobody knows whose model it is.

This is the problem Models as a Service solves. Instead of every team running their own stack, a shared gateway exposes models as API endpoints — with authentication so only authorised applications can call them, rate limiting so one team can't starve another, and usage metering so you can see exactly who is using what. Teams get the same model access without the operational overhead, and the platform gets visibility across the whole organisation.

That's what Exercise 4 covers.
